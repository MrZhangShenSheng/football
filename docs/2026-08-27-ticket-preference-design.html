实票偏好档案设计（ticket preference）

2026-08-27 · 作者 sszhang · 状态：设计已确认，同日实施 · 前置：实票账本（docs/2026-08-25-tickets-design.html）

1. 问题

boldplay 出票卡与用户实票口味完全脱节：生成器产出平串（HAD 4串1/5串1 + A-MIX 4串1 平串、倍数反算、档位 8/10/6 元），而 6 张实票全部是容错串（4串11 / 3场混串）、固定 2 元/注、重口玩法（CRS×11 / HAFU×5 / TTG×4 / HAD×2）、带双票对冲习惯——结果是 6/6 票 source: manual 自选，出票卡生成器没有承载任何用户偏好。

boldplay 出票卡用户实票（T001~T006）
形状平串：HAD 4串1×2注 / 5串1×3倍 / A-MIX 4串1容错串：4串11（6×2串1+4×3串1+1×4串1）/ 3场混串（2串1×3+3串1×1）
玩法HAD 为主 + A-MIX 混合重口：CRS/HAFU dd/TTG 极端值，HAD 仅 2 腿
注金档位 8/10/6 元，倍数反算固定 2 元/注，票面 8~22 元
对冲无双票同骨架换 1 腿（T002/T003、T005/T006）

2. 定位（方案 B：纯知识库）

data/06-tickets/preference.json = 静态手写的实票偏好档案，skill 会话在出方案/组票环节读它对齐口味；boldplay、backfill 等代码一律不读不写。理由：6 张票样本小，不值得建自动统计链路；"偏爱容错串搏回血""双票对冲"这类策略意图机器统计不出来，只能人写（YAGNI）。

分层职责——偏好档案是组装器不是选腿器：

层谁负责偏好档案能否复现
选腿（哪场、哪个具体比分）当轮预测流程（DC 融合 + EV 扫描 + 临场情报）否
组装（几串几注、多少钱、怎么派彩）preference.json是

playTaste 玩法全集（22 条腿精确统计）：

玩法universeband（口味带）historyavoid
CRS31项（比分29+胜/平/负其他）小比分胜方型：净胜≤2 且总进球≤32-0×6，1-1/0-1/2-1/1-0/3-0 各1长尾"其他"、大比分4-0+
HAFU9项（半场×全场）dd 为主力，aa 次之dd×4，aa×1反转组 ad/da；hh 强队慢热陷阱（8-26 教训）
TTG8档（0~7+球）两端极端：0球/5球0球×3，5球×1中间档2-3球（从未入票）
HAD3项（主/平/客）仅高赔价值主胜或串内托底主胜@4.05×2低赔热门单独成腿
HHAD让球胜平负—从未入票开放尝试：EV>0 且分歧合规才进，不作默认

4. 接入方式（3 挂点，代码零改动）

  1. skill/SKILL.md 出票卡环节（主挂点）：boldplay 三档展示后、AI 把系统方案翻译成用户形状时，读 preference.json 按 shapes/playTaste 组装。
  2. 协议表"我买了/出票了"：建档时用档案预填默认形状（2元/注、容错串），用户只口述差异；票面与档案不符时 AI 警觉追问而非默默推形状（防 T005/T006 漏腿类事故）。
  3. CLAUDE.md 目录结构：data/06-tickets/ 描述补 preference.json。

5. 维护纪律

  • 口味变化用户口述 → 手改 + 更 lastUpdated/sampleSize + git commit（git 历史=变更凭证）。
  • 被动校验：每次新票入账，AI 核对票面是否被档案覆盖；出现档案外的形状/玩法/注金（如首次 HHAD）提醒用户更新档案再收档。
  • 升级触发线（现在不做）：sampleSize ≥ 20 时偏好统计才有代表性，届时考虑结构化维度自动重算。

6. 回放验收（6/6）

档案落盘后逐张回放：给定 T001~T006 每张票的腿集合，档案规则推导形状/注数/金额/派彩规则，与 tickets.json 实际票面对照。6/6 全对收工，有错补维度重验。手工对照，不写代码——档案本来就是给 AI 读的，AI 对得上就是检验通过。

7. 实施顺序

git pull（单写会话纪律）→ 写 preference.json → 回放 6/6 → SKILL.md + CLAUDE.md 挂点
→ pytest 全量（落盘新 JSON 纪律）→ git commit（设计文档+档案+挂点一起）
