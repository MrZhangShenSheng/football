〇、立项背景与预期管理

大哥立项原话：「已经跑了这么多版本的测试了，我觉得每场的地基都不稳——预测模型的每一步的细节都是不清晰的，方案设计也是很粗糙的。」

翻译成工程语言：端到端指标存在（方向 64.4% / 比分 4.3%），但没有任何一步有自己的误差预算——错一场无法定位是哪步的锅；方案层（v16~v34 四线合流）已证明无 alpha，粗糙的本质是方案目的从未被定义。

预期管理（入档为验收原则）：本工程成功标准 = 每步有账可查，不是保住现有组件。哪怕审计后链路缩成「市场锚 + 结构先验 + 包装」，也是地基稳固——审计不是给现有系统续命。

范围 = 生产链（run.py → DC → V3W → 融合 → 战意/评级 → 假设层 → 五挡 → 出票）；v-series 研究脚本归档不动。

一、总体架构（四阶段 · P1/P2 并行启动）

方法论切分：P1/P2 管前向（今天的预测开始落证据链，历史补不了——输入没存档）；P3 管回溯（hist_odds 12.9k 场 + λ 缓存 6327 场重放）。两者共用同一套步骤分解：前向回答「这场怎么算的」，回溯回答「这步值不值」。

四条铁设计：① fail-open——仪表异常只警告不中断，预测主流程永不为 logging 挂掉；② 幂等——按（开赛日, matchId, step）键去重，重跑覆盖同键；③ 键口径=开赛日（物理比赛日，与 lineup_watch 一致；销售日只活在票务层）；④ schema 带 version 字段——加字段兼容，改语义升版。出票前跑完整性检查：九步缺哪步标注出来，不补造。

生效时点：会话登记纪律（S8/S9）与出票前完整性检查随 P1 上线即写入 SKILL.md/CLAUDE.md 预测协议——不等 P4。

四条方法论硬规矩：

① 时间线=v32.1 五道纯净闸（日期硬切零重叠 / fit-only 统计 / 同日先算后更 / 对照同切 / 弱泄漏交底）+ λ 缓存重放——不是 strict_merged（那是 TeamStats 流的纪律，勿混用）；

五、P4 · 按证据重构

拓扑序审判（从最下游往上游判，杜绝「中性且下游依赖」后门）：S9 方案 → S8 假设 → S7 矩阵 → S6 融合 → S5 去水 → S4 λ → S3 DC → S1/S2 数据。下游被 kill 的专用上游跟随 kill（例：比分端整体 kill → ρ/矩阵专用组件下链）。

判定规则动作验证方式
kill贡献 CI 上限 < 0，或下游唯一消费者已 kill下链 + 删代码删件=全链回放不降级
fixCI 跨 0 但有已知缺陷（系数过期/覆盖不足）换件或重拟合后重审换件=新旧影子并跑一周不降级才切换
keepCI 下限 > 0，或中性且 ≥1 个存活下游依赖留任 + 文档化——

产出：幸存链架构文档（HTML·五层：数据/市场锚/结构先验/独家信息/包装）+ 生产协议简化（CLAUDE.md/SKILL.md 更新）+ 幸存链注册表 surviving_chain.json（生产组件白名单：每组件挂 PASS 凭证=贡献 CI+审计日期，生产脚本启动校验——不在表/凭证过期→拒跑或降级标注）。注册表即机器闸门：约束未来一切迭代的物理层（大哥拍板 2026-10-11「以后的迭代模型也需要遵循这一套理念」，铁律 15）。「五代同堂」在证据锁定的范围内解决。
