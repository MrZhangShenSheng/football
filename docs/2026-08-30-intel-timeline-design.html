赛前情报时序库设计（intel-timeline）

日期：2026-08-30 · 状态：待大哥终审 · 关联：SKILL.md v5.3 / attribution 管线 / 05-trends 目录

1. 背景与动机

2026-08-29 晚 T010 出票后的临场扫描暴露了数据易失性问题：sporttery_matches.json 每次刷新整体覆盖，历史赔率状态（如 1:0 从 25→28 的调价过程）赛后永久无法重建；临场扫描的判断结论只存在于对话中；insight 情报虽按 matchId 持久化，但同场多次拉取只留最后一版，无时序。

大哥的三个诉求：① 临场扫描信息即时整理落盘；② 以后每次/每天收集自动记录；③ 将来把积累的数据设计成影响因子微调模型（因子去向先不锁定，数据只管结构化留痕）。

本设计新建「赛前情报时序库」子系统：在数据获取点埋钩子自动落盘，回填时挂赛果对齐桥，为将来因子验证提供零人工对账成本的原料。

2. 目标与非目标

目标（本期实现）非目标（YAGNI，明确不做）
① 赔率时序：刷新钩子自动落盘，diff 增量链，全五池
② 情报时序：insight 拉取即摘要落盘，时序保留
③ livescan：临场扫描结构化落盘（signals+threat 枚举）
④ 赛果对齐桥：backfill 挂 preSnapshots 指针（matchId 键）
⑤ SKILL.md 纪律固化 + run.py snapshot 手动补拍 		· SQLite（仓库既定 500 文件触发线之前保持文件制）
· _index.json（一天≤3文件，glob 兜底，检索铁律8）
· 因子设计/消融（远期，走 corpus→attribute→ablate 现成管线）
· 历史数据回补（不可再生，legacy livescan 双格式兼容即可）
· 定时任务（已选型：刷新埋钩子+手动子命令）

2.5 核心设计原则

采集宁全勿缺，分析宁简勿繁——没记的字段是永久丢失不可回补（因子去向未锁定 ⇒ 任何池都可能是信号源）；分析侧按需取用，多余字段不构成负担。

3. 总体架构与数据流

4. 三类文件 schema

4.1 odds 时序（全五池 · diff 增量链）

{
  "date": "2026-08-30", "type": "odds-timeline", "schemaVersion": 1,
  "snapshots": [
    { "at": "2026-08-30T10:15+08:00", "trigger": "run.py update", "base": true,
      "matches": [
        { "code": "周日001", "matchId": 2041160, "league": "意甲",
          "home": "X", "away": "Y", "kickoff": "2026-08-30 19:00",
          "had":  {"h":1.1,"d":6.4,"a":14.0},
          "hhad": {"goalLine":-1,"h":2.1,"d":3.2,"a":3.4},
          "crs":  {"s01s00":28.0, "...": "31项"},
          "ttg":  {"s0":8.5,"...": "8档"},
          "hafu": {"hh":3.1,"...": "9键"} } ] },
    { "at": "2026-08-30T14:20+08:00", "trigger": "临场复扫", "base": false,
      "changes": [ { "code": "周日004", "crs": {"s00s02": 24.5} } ],
      "removed": ["周六026"] }
  ]
}
  • diff 粒度：场内玩法项级；新上考场次全项进 changes（天然兼容）；元数据变化（kickoff 改期/队名勘误）允许进 changes 整场标记
  • 回放规则：base 全量 → 依次应用 changes；diff 基准 = 当日文件最后一版回放态
  • 副产品（存量 bug 修复）：日首版全量带 matchId = 留档了 code→matchId 映射。原系统停售后 cache 被覆盖、赛后从编号无法反解 matchId——此映射天然持久化
  • 体积：全五池日首版 ~220KB，增量版日常几 KB（实测 49 场仅 1 场调价）；约 90MB/年，跨年归档压缩（§8）

4.2 intel 时序（按需场次 · 摘要+指针）

{
  "date": "2026-08-30", "type": "intel-timeline", "schemaVersion": 1,
  "entries": [
    { "at": "...", "matchId": 2041147, "code": "周六027", "league": "意甲",
      "fullFile": "engine/cache/sporttery_insight_2041147.json",
      "injuries": { "home": [ { "name": "耶尔德兹", "pos": "前锋", "apps": 1, "starts": 1, "keyPlayer": true } ],
                    "away": [], "d": 1 },
      "rank": {"home": 8, "away": 16},
      "form": {"homeLast10": "6胜2平2负", "awayLast10": "3胜2平5负",
                "homeGoalAvg": 1.1, "awayGoalAvg": 0.8},
      "h2hSummary": "7胜2平1负" }
  ]
}
  • keyPlayer 判定沿用修正系数9标准：apps≥2 且 starts/apps≥0.7；d = 主−客缺阵数（先主后客，带符号，正值=主伤更重）
  • 同场赛前多次拉取 = 多条 entry 并存（时序语义，修复"只留最后一版"缺口）
  • h2hSummary 保持粗摘要定位（H2H 仅叙事参考不进权重，检索铁律5），明细走 fullFile 指针

4.3 livescan 事件（扫描判断 · 结构化）

{
  "date": "2026-08-30", "type": "livescan", "schemaVersion": 1,
  "scans": [
    { "at": "...", "trigger": "T010出票后监控",
      "verdict": "无真边际无可修订",
      "matches": [
        { "code": "周六027", "matchId": 2041147,
          "tickets": [ { "ticket": "T010", "pick": "0:1", "frozenOdds": 25.0 } ],
          "oddsNow":  { "crs": {"0:1": 25.0} },
          "signals": { "oddsMoveVsFrozen": 0.0,
                        "keyPlayerOut": { "team": "home", "player": "耶尔德兹" },
                        "formMismatch": "帕尔马场均0.8球支撑不了客胜2球" },
          "threat": "high",
          "note": "自由文本：尤文火力降利好0:0(T009)不利好0:1" } ] }
  ]
}
  • threat 枚举：high / midhigh / mid / low；trigger 枚举：run.py update / 预测Step1 / run.py snapshot / 临场复扫 / 出票后监控 / 用户要求
  • signals = 因子验证直接可读的结构化原料；note = 自由文本
  • oddsNow 声明为冗余字段（自包含便于单场回看），分析时以 odds 时序文件为准
  • 录入走 write_livescan() 校验函数（枚举/必填字段/schemaVersion），防手写漂移
  • 2026-08-29 legacy 文件保留原样（git=事实），分析脚本双格式兼容

6. 错误边界

情形处理
体彩 API 失败钩子跟随刷新成功才触发，无独立重试（刷新本身已有降级链）
当日 odds 文件损坏/被手改回放失败 → warn + 降级为新 base 全量版（宁冗余不丢数）
并发写（双会话同时刷新）原子写（tmp+rename）+ 仓库单写会话纪律双保险
跨日新文件新 base（每日一次全量，可接受）
同场 insight 重复拉取多条 entry 并存（时序语义正确）
backfill 找不到该场快照preSnapshots 省略（部分场次无情报是常态）
空调价也落盘（"该时点无调价"本身是数据点）

7. 测试方案（脚本自测风格，无 pytest）

  1. trends_snapshot.py --selftest：fixture 三情形——①单项调价 diff 只出该项 ②新上考场全项进 changes ③停售进 removed；断言回放(base+changes) == 全量真值；元数据改期留痕
  2. 集成：run.py snapshot 连跑两次 → 第二次 changes 为空或极少 + 文件合法可回放
  3. 回填桥：造一场已回填记录（含 code→matchId 跨日解析），验证指针挂载且 lastOddsAt < kickoff
  4. write_livescan 校验：威胁度枚举外值被拒、必填字段缺失被拒

8. 容量与演进

  • 05-trends 文件量并入 500 文件触发线（与 02-results 合并计数，全局口径）
  • 跨年归档：旧年份目录 gzip（git 对压缩文件同样可 diff 存储）
  • schemaVersion 迁移规则：只加字段不删、旧文件不回改；分析脚本按 version 分支
  • 落盘文件随流程 commit 入库（git = 凭证，仓库惯例）

9. 远期衔接（开放问题 · 本期不实现）

因子候选（schema 已预埋）：oddsMoveVsFrozen（市场信号）/ keyPlayerOut + d（阵容）/ threat 枚举 vs 实际命中（扫描判断质量）/ formMismatch（定性，需将来结构化）。

消融纪律不动摇：数据积累 ≠ 因子自动有效。验证走现成管线 corpus 积累 → attribution 新增因子键 → ablate 消融，无正增益即删（战意因子 2026-08-29 降级先例，两份独立分析一致结论）。

明示边界："每天必有档"做不到——钩子跟会话走，当天不开会话则无快照（选型时已确认：刷新埋钩子+手动补拍，非定时任务）。

10. 决策记录（ADR）

#决策理由备选与否决原因
D1范围=混合：赔率全量+情报按需因子验证样本量 vs 接口频率风险的平衡全量全套（49次insight/天有封禁风险）；只记关注场（样本不足）
D2触发=刷新埋钩子+手动子命令零新增基础设施，数据获取点天然触发定时任务（不开会话无档/7天过期/系统级要装权限）
D3因子去向先不锁定避免 schema 为臆想的因子服务预设修正系数层/DC层/选腿层（锁死思路）
D4方案B：结构化时序库+diff增量体积最小；matchId 聚合天然支持；回填桥让 attribution 零打通成本方案A原始快照（git膨胀+对齐重做）；方案C SQLite（违反500文件触发线架构决策）
D5全五池落盘没记=永久丢失不可回补；采集宁全勿缺三池 had+hhad+crs（省几十 MB 但ttg/hafu信号永失）
D6livescan 轻量工具化（write_livescan 校验）signals 是因子验证核心原料，格式漂移=原料污染纯纪律约束（软）；重命令行（过度）
D7原子写（tmp+rename）一行代码防竞态损坏→数据质量滑坡仅靠单写会话纪律（有窗口）
D8桥匹配键=matchId，窗口=比赛日±1天体彩编号每周复用；cache 停售后覆盖致 code 反解不可行code 匹配（跨周错配）；单日窗口（漏赛前夜时点）
