# football skill 瘦身与分层方案

## 评审结论

当前 football skill 的主要问题不是单条规则太多，而是**执行规范、历史变更记录、实现细节、案例教训和输出模板被长期叠加在同一个运行入口中**。根文件 `skill/SKILL.md` 已达到806行和约76.7KB，整个 skill 目录约148KB、1,548行。skill-creator 建议核心 `SKILL.md` 控制在500行以内；当前主文件明显超过这一边界。

本方案建议采用**保守分层、先迁移后删除、保留回滚点**的方式。目标不是删掉有效规则，而是将每次预测必读内容与只有特定任务才需要的内容分离。

## 主要冗余来源

### 版本历史占据运行上下文

根文件开头连续保留v4.0至v5.10的更新说明。它们适合审计和回溯，不适合每次预测都加载。历史条款中还反复出现“v4.x新增”“某日事故来源”等注释。建议主文件只保留当前生效规则和一行当前版本说明，将历史变更移到仓库 `docs/`，不再放入 skill 运行入口。

### 同一纪律在多个层级重复

“赔率不是概率”“不得编造数据”“出票前编号核对”“比分方向与精确比分分离”“同场只能一种玩法”“共享腿要按耦合概率计算”等内容同时出现在铁律、执行步骤、输出规范、复盘章节和最终清单中。保留一处完整定义，其余位置只保留短引用或检查项即可。

### 主流程混入实现细节

`SKILL.md`同时规定了API缓存路径、触发环境变量、脚本入口、JSON字段、回填链路、ablate关键词和历史事故。这些信息对工程执行有用，但不应该与预测判断规则混在同一层。建议建立“决策规则”和“工程接口”两类 reference。

### 旧版本兼容说明没有退出机制

主文件同时描述legacy、amix、freq-band、v5.5翻身档、旧三段式和新三档制。兼容路径如果仍在生产使用应单独保留；如果只是回测或回滚用途，应标注为“非默认路径”并移出主流程。否则模型容易同时执行互相冲突的旧规则。

### 根 skill 与临场子 skill 边界不够硬

临场子 skill 已经重复说明数据来源、伤停调整、赔率复扫、EV表述和比分校准。建议根 skill 只负责全局预测和出票，子 skill 只负责指定比赛的临场复核，并通过固定输入输出字段衔接，不再复制全局玩法和档案规则。

现有 `play-rules.md`、`score-calibration.md` 和 `score-odds-template.md` 不必立即重写。第一阶段可以保留文件名，只在根 skill 中建立清晰的加载条件；第二阶段再合并内容，减少长期维护的文件数量。

## 主文件建议保留的内容

主 `SKILL.md` 只保留以下六部分：

1. **触发范围与当前默认模式**：说明适用于哪些足彩任务，以及默认使用哪条生产链。
2. **十条以内的核心硬约束**：只写不可违反的规则，每条不超过两句。
3. **八步执行流程**：赛事采集、数据就绪、概率锚、深度分析、玩法匹配、临场终审、输出、回填复盘。
4. **阶段加载表**：明确什么时候读取赔率、玩法、比分、系数、临场和schema references。
5. **统一输出字段**：把概率、赔率、EV、证据等级、形状族和数据缺口定义一次。
6. **最终自检清单**：只保留机器或人工必须勾选的项目，不重复解释规则。

建议把现有13步合并为8步。Step 1与Step 1.5可合并为“采集与预筛”；Step 2与Step 3.5可合并为“概率锚与融合”；Step 6与Step 6.5可合并为“玩法与临场终审”。这不会改变生产逻辑，只会减少导航层级。

## 迁移与删除策略

### 阶段一：只做分层，不改变规则

将当前主文件中的长段落复制到对应 reference，主文件改成摘要和加载指针。保留原文备份，并用git提交。此阶段不删除任何有效内容，也不改变默认路径。

迁移优先级如下：

| 优先级 | 迁移内容 | 目标文件 |
|---|---|---|
| 立即 | API、缓存、失败降级和触发器 | `data-and-fallback.md` |
| 立即 | JSON schema、回填、CLV和复盘字段 | `record-schema.md` |
| 立即 | 官方玩法、抽水、M串N、耦合概率、出票核对 | `ticket-rules.md` |
| 立即 | 赔率双锚、去水、EV、CLV和“赔率不等于概率” | `odds-and-probability.md` |
| 立即 | freq-band、比分形状、1:0/0:1/2:0/2:1/0:2/1:2模板 | `score-selection.md` |
| 后续 | 系数和历史事故 | 继续按需读取 `coefficients.md`、`lessons.md` |

### 阶段二：删除重复内容

完成引用替换并通过样例任务后，删除主文件中的历史版本说明、事故长叙述、同一规则的解释性重复段落和旧路径说明。历史内容移动到仓库 `docs/skill-history/`，不作为 skill reference 自动加载。

### 阶段三：整理临场子 skill

将临场子 skill 的公共规则改成对根 skill reference 的引用。它只保留：比赛身份核验、最新伤停和首发、赔率复扫、临场概率更新、替代玩法判断和临场报告字段。根 skill 不再重复临场细则。

## 预计收益

| 指标 | 当前 | 保守目标 |
|---|---:|---:|
| 根 `SKILL.md` | 806行 | 300–380行 |
| 根文件体量 | 76.7KB | 28–38KB |
| 每次默认读取内容 | 主流程+全部历史堆叠 | 核心规则+任务相关reference |
| 比分任务读取 | 规则分散在主文件和3个段落 | 统一读取 `score-selection.md` |
| 出票任务读取 | 主流程、玩法和清单多处交叉 | 统一读取 `ticket-rules.md` |
| 历史教训污染主上下文 | 高 | 仅复盘或冲突时加载 |

在不删除任何生产规则的前提下，预计每次普通预测的有效上下文可减少约40%–60%；根文件本身可减少约53%–63%。

## 必须保留的安全护栏

瘦身时不应删除以下内容，只允许改成单一权威定义并在其他位置引用：

- 不编造数据，以及数据缺口必须显式标注；
- 体彩编号、联赛、主客队和时间的三重核对；
- 赔率来源、时间戳和去水口径；
- 模型概率、市场概率、历史频率和当前比分赔率不得混为一谈；
- freq-band的生存阈、形状带和不足腿数关档纪律；
- 零封族与对手进球族不得伪装成独立容错；
- 同场限一种玩法、不同场可混串；
- 共享腿的耦合命中率计算；
- 负EV不进入正式方案；
- 预测必须回填赛果并完成复盘；
- 票面最终核对和失败降级追查。

## 验收标准

### 文档层

- `skill/SKILL.md` 不超过400行，frontmatter和触发词保持不变。
- 每条硬规则只有一个权威定义，其他位置只引用。
- 默认生产路径只有一条；legacy和amix明确标注为回测或回滚路径。
- 所有reference都写清“何时读取”和“不可替代什么”。
- `quick_validate.py`通过，Markdown无断链和git diff空白错误。

### 行为层

用以下五类任务做回归，不要求预测结果完全相同，但要求规则行为不变：

1. 普通全局预测：能完成采集、概率融合、分级和三档方案；
2. 仅比分任务：能读取常见比分赔率模板并输出形状族；
3. 临场复核：能核验伤停、首发、赔率复扫并明确是否改票；
4. 票据登记：能校验编号、玩法、倍数、共享腿和回款；
5. 赛后复盘：能回填结果、统计命中和记录教训。

### 回滚条件

如果回归任务出现以下任一情况，暂停删除阶段并恢复上一提交：关键字段丢失、旧路径被误当默认路径、负EV选项重新进入正式方案、比分形状重新全部集中为零封族、同场多玩法违规或共享腿概率被独立近似替代。

## 建议的采纳选项

### 方案A：低风险整理，推荐

只做阶段一和阶段二的轻量版。主文件缩到约450行以内，保留现有reference文件名，不重构工程脚本。风险最低，收益主要来自删除版本历史和重复解释。

### 方案B：标准分层，建议最终采用

按目标结构拆成决策、赔率、比分、玩法、数据和schema六类reference，主文件缩到300–380行，同时压缩临场子 skill。规则本身不变，但维护边界清晰，是收益和风险最平衡的方案。

### 方案C：激进重写，不建议立即采用

以新的v6.0主文件完全重写流程，并合并多个reference。虽然体量可以降到250行左右，但容易在迁移中遗漏旧护栏，也会增加回归和审计成本。除非后续确认当前生产链已有自动化测试覆盖，否则不建议直接使用。

## 本轮建议

建议先采纳**方案A作为第一步**，确认瘦身后没有改变日常输出，再升级到方案B。当前不建议直接删除历史教训、系数表和临场子 skill；它们应从“默认上下文”降级为“按需上下文”，而不是消失。

本方案没有修改 football skill 的规则文件，仅完成审计和可回滚方案设计。
