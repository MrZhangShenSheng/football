〇、问题定义（第一性原理）

目标：让"回填赛果 → 模型升级"成为自动化闭环，持续提高预测准确率（RPS/CLV），且每次升级可验证、可回滚、可归因。

先管理预期：回测实证纯市场（Pinnacle 收盘）RPS 0.1850 是最强基线。击败市场的历史数据极难，本系统的目标不是"打败市场"，而是： ① 消除已知盲区（31% 场次无模型覆盖）② 删除负增益的手工系数 ③ 让融合权重由数据而非拍脑袋决定。 方向正确率的现实上限 ≈ 市场本身（~58%）± 2pp，杠杆主要在覆盖面和纪律，不在算法魔法。
31%本轮 52 场中非 fd 联赛（日职/韩职/沙特/北欧…）
44%场次真正用了 DC 模型（23/52），其余纯市场锚
-5.8%7 单 CLV 均值（体彩 12.9% 抽水的结构性负值）

二、总体架构：五件套闭环

虚线 = 跨轮循环；实现顺序 = ①⑤（底座）→ ④（杠杆）→ ②③（攒数据后自动可跑）

三、模块详细设计

① corpus.py — 学习语料汇总（数据底座，最先做）

项设计
输入data/02-results/*.json（跳过 _h2h_index）+ 联赛画像
输出data/04-summaries/corpus.json：全量 records 合并视图（按 code+date 去重，后写覆盖）+ 就绪度统计
就绪度字段n_total / n_result(已回填) / n_clv / n_pfinal / by_league / by_star / by_grade 分桶计数 —— ②③④ 的门槛判断都读这里
触发每次"回填赛果"后自动跑；输出一行就绪度摘要（如 语料 52 条 · 已回填 8 · CLV 7 · 距校准门槛还差 92）
成本~60 行纯本地合并，零网络

为什么先做它：所有下游分析都消费同一份语料，先统一数据源避免各脚本各扫各的、口径不一。

② calibrate.py — 融合系数重校（攒够数据自动可跑）

项设计
算法corpus 中含 p_final(=市场锚) 与赛果的场次 → 网格搜索 a∈[0,0.8]×0.05, b=1 固定，最小化平均 RPS（复用 backtest.py 的 rps()，不重写）
门槛n ≥ 100 场已回填（fusion.json 原有约定）
护栏① 新 RPS 改善 < 1% → 不升级，只记录 ② 新 a > 旧 a × 1.5 → 拒绝（防小样本把模型权重顶上天）③ 同时输出按联赛分层的样本量警告
写回fusion.json 更新 a/b + lastTuned + tunedN + 依据；旧值进 fusion_history.json
校验升级后在下一个回测周期对比新旧系数 RPS——变差即回滚（history 里有旧值）

③ ablate.py — 修正系数消融（纪律执行器）

项设计
对象8 个手工系数：开季分档 / 波动系数 / 保级平局保护 / 用户反馈 / 首回合保护 / 让球反推 / 叠加封顶 / 战意状态机
方法corpus 每条 record 已存 p_final（修正前）与 p_adj（修正后） → 按系数触发与否分桶，对比两列的 RPS/Brier：修正后 ≤ 修正前 = 正增益
门槛每系数触发样本 n ≥ 50 才下结论；不足的标"观察中"继续攒
动作正增益 → SKILL.md 系数标 ✅已验证；负增益 → 标 ⚠️删除或降参考；输出 diff 建议，人审后改 SKILL.md（不自动改文档）
巧点p_final/p_adj 双列留痕是 v4.1 就有的设计，消融器几乎零额外采集成本——这个设计已经在赚钱了

④ 非fd联赛赛果入库 — 最大准确率杠杆（大哥已定高优先）

现状：本轮 52 场，非 fd 联赛 16 场（31%）：日职 3 / 韩职 3 / 沙职 2 / 日乙 2 / 德国杯 2 / 芬超 1 / 瑞超 1 / 荷乙 1 / 德超杯 1。这些场次 dc_used:false，预测纯靠市场锚+手工修正，赛果也不进任何模型。

项设计
数据链ESPN 按日赛果（已实测：espn_fetch.py results jpn.1 20260820 20260821 ✅）→ 转成 dc_fit 的 matches 格式（date/home/away/hg/ag，队名经 _aliases.json 规范）
存储data/02-results/league/{league}_matches.json 累计追加（与按日期文件并存，专供拟合）
拟合攒到 每联赛 ≥30 场（约一轮全联赛 5~8 场 × 4~6 轮）→ dc_fit 扩展 --source local 拟合 {league}_dc.json；60 场后参与 normal 服务
冷启动ESPN 还能拉历史赛季赛果（2025 赛季整季 ~340 场/联赛）→ 一次性回填去年整季，第一轮就能出模型，不等几周攒数据
队名映射复用 data/01-teams/_aliases.json + cn_fetch teams 子命令补中英对照；映射不上的场次丢弃并记日志（宁缺毋滥）
防污染杯赛（德国杯/德超杯）单场淘汰制不拟合（战意/轮换噪声大），只入库联赛
优先级顺序：日职（3场/轮，稳定）→ 韩职（3场/轮）→ 沙特（2场/轮）→ 北欧四联赛（体彩上架时才有）。历史赛季回填优先于增量攒。
2026-08-23 追记：韩职历史源已落地——ESPN 不覆盖韩职，改走体彩票源（sporttery_fetch.py league-results korea，zqlszl 口径 90 天分段），三季 597 场回填 + korea_dc_v1 已发布；run.py learn 接 SPORTTERY_LEAGUES 链路。详见 SKILL.md v4.8 版本日志。

⑤ 模型版本存档 — 升级可验证/可回滚/可归因

元数据字段（.meta.json）用途
n_train / date_range / source(fd|local-espn)训练集归因：什么数据练的
holdout_logloss / rps_baseline(市场)发布门槛：不优于当前版+市场基线 → 不发布
replaced_version / replaced_by / reason版本链：谁替谁、为什么
createdBy = sszhang pipeline责任人约定

版本策略取最简：不搞自动 ML 流水线，快照 + latest 路由 + git diff 足够。500 文件迁移 SQLite 前不动这套。

四、数据流与触发时机（谁在什么时候跑什么）

触发自动执行产出
"回填赛果"①espn 赛果回填 → ②corpus.py 重算 → ③就绪度一行摘要corpus.json 更新
corpus 就绪度达标（n≥30）提示"日职/韩职可拟合"→ dc_fit --source local新 {league}_dc_v1 + meta
corpus n≥100calibrate.py 自动跑（有护栏）fusion.json 或"不动"结论
每系数触发 n≥50ablate.py 分桶报告（人审）SKILL.md 修订建议 diff
每次升级（②④产出新版本）快照 models/ + git commit可回滚版本链

五、实施排期（建议两批）

批次内容规模验收标准
P1 底座+杠杆
约 1 次会话		①corpus.py + ⑤models 存档机制 + ④ESPN 历史赛季回填（日职/韩职/沙特）+ dc_fit --source local~250 行 + 测试日职/韩职/沙特各产出 _dc_v1 + meta；corpus 就绪度摘要正确；42 测试不破
P2 分析器
数据攒够后		②calibrate.py + ③ablate.py（挂 corpus 门槛，未达标自动跳过并提示）~180 行 + 测试未达门槛正确跳过；护栏三件套生效；history 正确记录

P1/P2 分批原因：②③现在没有足够数据验证收益，先建管道攒数据；④是唯一"今天做下周就见效"的项（历史赛季回填当轮生效）。

六、风险与对策

风险对策
小样本过拟合（n<100 就调参）硬门槛写死在代码里（不靠自觉）；护栏三件套；改善<1% 不动
ESPN 队名与体彩/别名对不上，脏数据进模型映射失败即丢弃+日志计数；拟合前 sanity check（场次数/进球范围）
版本膨胀（models/ 无限增长）每联赛保留最近 3 版 + 被替代版标记；git 历史兜底全量
CLV 均值 -5.8% 引发"模型没用"误读报告固定口径：体彩抽水结构性负值，评价用 DK 近似 CLV 的相对排序而非绝对值
杯赛数据污染联赛模型④明确只入库联赛赛果，杯赛场次标记排除

七、待大哥拍板的细节

  1. ESPN 历史赛季回填深度：只拉 2025 一季（~340场/联赛，当天可完成）vs 拉 2024+2025 两季（样本翻倍，2024 队伍换血对当前参数贡献存疑）？建议：2025 一季起步，ξ 时间衰减会让老数据权重自然归零
  2. calibrate 的 a 上限：护栏拒绝 a>0.6（现初始 0.4）还是更保守 a>0.5？建议 0.6，留出验证空间但封顶过拟合
  3. ablate 人审 vs 自动改 SKILL.md：建议人审——系数规则是文档语言不是代码，diff 给大哥过目再改
  4. corpus.json 是否进 git：建议进——它是"学习进度"的凭证，与预测记录同等待遇
